# DP pipeline feasibility

Retain the active frozen plan for this round. The earlier dual-DP memory rejection does **not** rule out running B DP alongside A nominal caching or A rear training. Historical GPU figures make that mixed pipeline plausible, but combined RAM/I/O residency and actual speed evidence do not justify changing the active main/waiter orchestration. No source, runtime, job or service was changed and no GPU experiment was launched for this review.

No corresponding mixed DP+cache/rear RAM bound was measured.

The storage evidence argues for caution about benefit, not impossibility. B DP's kernel task I/O counters record5164232105984 read bytes and127518 major faults, with a4GiB CUDA hotset and mmap of current B2 histories; this is task accounting across the stage, not measured SSD bandwidth. Concurrent A nominal regeneration reads the same immutable perception pool, computes a causal DP history and writes its own cache. OS pages can be shared but cache eviction/read amplification and CPU/PCIe/kernel contention remain unmeasured. Rear training eagerly loads all nominal records on CPU and has smaller GPU work; it competes less for perception I/O, but no mixed-run throughput measurement exists. Parent cache/rear device utilization sample means were roughly19%/29%; these are device-wide instantaneous samples, not worker GPU-time attribution or proof that their unused capacity adds linearly. B DP's12015.8s includes I/O/validation/waits; A's1326.1s timer covers recovery only and is unsuitable as full-stage speed evidence.

There is also less additional critical-path gain than “hide A rear” suggests. The current plan already overlaps A/B rear training. With no contention its tail is CA+CB+max(RA,RB). If A cache+rear runs while B DP, and B rear still follows B cache, the tail becomes max(max(DB,CA+RA),DB+CB)+RB after A DP. Using parent DB12015.8>CA+RA6026.4 and RA5798.2<RB5831.9, the ideal extra saving is only CA228.2s (3.8min), not A's5798s rear duration. Real parallel-rear contention could change this, but no paired throughput benchmark exists. A more efficient mixed schedule is possible in principle; a positive net saving is unproven and slowing B DP by a few minutes can erase the ideal gain.

Dependencies permit a future pipeline: A's selected epoch60 DP can generate A's own cache while B DP trains; B state_data statistics used for common rear normalization are already materialized. Role directories and per-process RNG are separate. However, the current reviewed wrapper explicitly requires both DP deployments, then serial own caches, and only two rear trainers may overlap. Its exact job, main/waiter sources, parallel registration and watcher identities are now frozen. A new pipeline needs a distinct reviewed wrapper/admission plan and updated immutable registration before a future run. Reusing one exact owner would allow normal descendant attribution; launching an unregistered new owner/argv would not. The watcher can pause both pipelines cooperatively for external work, while their resident memory remains; it offers no zero-interference guarantee.

Recommendation: keep this round's plan, use current runtime actual-cache admission for the two rears, and retain the mixed pipeline as a future measured optimization. The present evidence corrects the broad “DP+anything cannot fit” interpretation, but does not establish safe combined RAM or useful speedup.
